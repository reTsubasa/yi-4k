# YI 4K 1.10.7：一分钟预录的实现条件

日期：2026-11-10。对象为本机普通 YI 4K、1.10.7 `a8f840ce_r2746`，不是 YI 4K+。以下逆向来自本地 Ghidra 导出和 Capstone，没有 REA Evidence ID。本轮未修改相机、未启用隐藏设置、未执行任意 RTOS 代码。

## 结论

“平时保留最近一分钟，按快门后把这一分钟连同后续录像保存”的产品行为在这套硬件上有可行的软件设计，但**目前没有验证出可直接启用的原厂一分钟预录**。固件的 `VideoPref.PreRecord` 确实有配置结构和菜单回调；进一步追踪发现，当前 connected-camera 应用对相应操作走默认空处理，不能仅凭这个字段宣称已有功能。

优先方案是复用原厂硬件编码器，在 SD 上保存按关键帧切分的短段循环；触发时保留最近一分钟对应的段，继续保存后续段，再在相机内无重编码封装为可直接播放的 MP4。这个方案还没有在真机实现。纯 RAM 环形缓冲可作为低码率备选，不能承诺在 4K 高码率下保存一分钟。

## 已追出的配置与分派链

| 入口 | 静态观察 | 能说明什么 |
|---|---|---|
| `A018CA78`，片段 `A018CC8C..A018CCC8` | 将 `A055D774` 的 `VideoPref.PreRecord` 复制到条目名，条目大小 `0x88`；条目 `+0x80=9`、`+0x84=1` | 该名字对应 preference 结构 **+9 的一字节字段**，不是“9 秒” |
| `A018C674`、`A018C8EC` | `A1055CD4` 指向 `A1055AD4`；复制完整 preference `0x140` bytes | 定位结构与运行时指针；不需要猜任意内存地址 |
| `A017F1A8` | 菜单选择变化时取选项表值，写 `*(pref+9)`，发送 `F0010303` | 有菜单残留；本轮未恢复全部选项表和界面可达性 |
| `A019A18C`，调用点 `A019A28C` | 启动把 `*(pref+9)` 送入 `A021F768` | 配置会被传给录像库的状态结构 |
| `A021F768` | 对 `A13C82BA` 执行读改写，仅保留入参低 **4 位** | 写入十进制 60 会变成 12，不能把该字段直接当作一分钟开关 |
| `A0113808` | `F0010303` 在应用已就绪时转给操作 `0x2C` | 到了具体录像应用操作分派 |
| `A01282E0` | 真实 ARM 跳转表位于 `A01282FC`，`table[0x2C] = A012A094`；该目标清零返回值并回公共出口 | **当前分派中的 0x2C 为默认空处理**，不是已恢复的预录启动 |

现有 Ghidra `references.tsv` 对 `A13C82BA` 只列出 setter 内 `A021F770 READ` 与 `A021F77C WRITE`；未找到读取低四位来驱动保留帧的直接消费者。这是有界负面证据：不排除别名、间接访问、未识别代码或其他应用实现。结合真实跳转表，不能把“改配置即可预录”当作实施方案。

原始反编译位于 [full/decompiled](../artifacts/device/2026-11-09-linux/rtos-analysis/full/decompiled/)，`A018CA78` 全函数当时反编译超时，因此字段结论由对应 ARM 片段和通用 schema 消费者 `A018F334` / `A018F5C0` 交叉确认。现有 API 的只读回包未列出 prerecord；`rec_mode` 为普通、延时、循环、录中拍照和慢动作，`loop_rec_duration` 为 5/20/60/120 分钟或 max。这些循环录像时长与“触发前一分钟”不是同一能力。见 [options.json](../artifacts/device/2026-11-10-feature-api/options.json)。

## EventRecord 库能否复用

二进制还包含一套事件录像 MP4 封装代码，值得复用，但没有证据证明它就是用户需要的待机预录：

- `A01F845C`：字符串明确标识 `AppLibFormatMuxMp4_Open_EventRecord`。创建文件流、视频/音频 track、MP4 muxer 和 FIFO，并填入原厂 GOP、帧率、分辨率和采样率。音频 bitstream 区间中出现 `0xA00000`，不能将此数解释成“一分钟视频缓冲”。
- `A01F8E68`：原生回调片段检查 `A13C35CC` 后调用 `A01F845C`；`A01F8E80` 请求事件结束；`A01F8F08` 等待完成并关闭事件 mux 及关联对象。
- `A012C98C`：只有 `A0FB334C == 1` 才发送应用操作 `0x1D`；否则打印“Block eventrecord when system is not in recording”。这表明这条入口设计为**录像中触发事件录像**。
- 同一个 connected-camera 跳转表的 `0x1D` 也指向默认 `A012A094`，`0x1E` 同样默认；`0x1F` 则保留了结束调用。因此，库存在与应用完整接通应分开判断。

没有完成的部分是：事件库历史 FIFO 保留策略、Start 回调注册的可达路径、触发前时长参数、视频 bitstream 占用/溢出处理及切换应用后的状态语义。本轮不建议通过盲发事件或更改 BSS 字节试启用这条残留路径。

后续复核见 [编码流与 EventRecord 静态契约](prerecord-static-stream-contract.md)：`A01F8EBC` 虽构造了开始/关闭回调描述符，但实际调用的是注销器 `A01F0F2C`，不能当成已找到 EventRecord 的注册入口。另一个含 `IDR`/`SPS/PPS` 的通用格式路径是从 stream 向 FIFO 喂帧的输入方向，暂不属于已恢复的编码输出切段接口。

## 一分钟需要多少空间

预录保存的是硬件编码后的流，不必存原始 YUV，也无需 SharePreview。下表仅计算视频 payload，未包含音频、mux 索引、GOP 超出一分钟的部分和工作余量；Mbps 按十进制定义。

| 实际视频码率 | 一分钟视频数据 | 对此前 idle 应用池空闲量的比例 |
|---|---:|---:|
| 20 Mbps | 150 MB / 143.1 MiB | 64% |
| 30 Mbps | 225 MB / 214.6 MiB | 96% |
| 60 Mbps | 450 MB / 429.2 MiB | 192% |
| 100 Mbps | 750 MB / 715.3 MiB | 320% |

此前真机应用 byte pool `A0FD7114` 的总 Available 为 **234,597,172 bytes / 223.7 MiB**，见 [诊断报告](device-1107-console-and-readiness-validation.md)。这是当时 idle 总余量；不保证连续分配、录像时余量或将这些内存全部占用后的稳定性。即使 20 Mbps 算术上装得下，也仍需实际测量音视频 FIFO、编码器和自定义 EIS 同时工作的峰值。60/100 Mbps 不能靠这份池余量承诺纯 RAM 一分钟。

SD 方案在 100 Mbps 下每分钟约写 750 MB，因此要接受持续写卡、耗电、发热及卡磨损；开启预录时编码器已经在持续工作。产品里的“开始真实录像”应表示**提交保留并进入长期保存状态**，不能表示触发时才启动编码器。

## 二开的状态机和验收

建议统一 `commit_recording()` 动作，让相机实体快门、所选开关键短按事件、相机原厂语音识别结果和 App 发起的开始操作都进入同一个状态机；开关键具体短按/长按语义还需要独立核实，不能拦截长按关机或直接假定与快门相同。App 不负责生成或识别相机语音。

1. `OFF`：普通取景；`ARMING`：创建片段目录与原厂编码/FIFO；首个可解码 IDR 后进入 `ARMED`。
2. `ARMED`：维护最近至少 60 秒的完整 GOP/短段，删除超过窗口且未被保留的自有文件。与原厂 `loop_record` 区分，禁止改删用户已有素材。
3. 收到 commit：原子固定当前环形段清单，停止淘汰所需段，转 `RECORDING`；重复触发只确认当前状态，不重新启动编码器。
4. stop：封完当前段，转 `FINALIZING`，在相机内复用 mux 或新增流式 remux，发布完整 MP4；失败保留段和 manifest。若设置了继续预录，再重新进入 `ARMED`。

关键工程门槛是全分辨率编码 bitstream/FIFO 的安全订阅和生命周期、按 IDR 开始且带正确 SPS/PPS 的片段、音视频 PTS/DTS 与时间基、跨段无丢帧/重帧、码率峰值、mux 索引内存和掉电恢复。若从触发前最近 IDR 开始，实际前置时长可能比 60 秒略长；若要求精确截断到某一帧，需要验证 MP4 edit list 等兼容行为，不能直接从非 IDR 帧截 H.264。

先验收 5 秒窗口，再提高到 15、60 秒；每档至少检查首次播放、声音同步、触发点两侧画面连续、设置变更、满卡、拔卡/掉电、重复点击、长时间温升和退出后的原厂录像恢复。最终验收条件是：相机独立待机预录，实体按钮一次提交，文件包含触发前至少一分钟和后续内容，手机/电脑直接播放，无需电脑合并。

## 复现与证据边界

运行 `.venv-reverse/bin/python scripts/analyze_prerecord_routes.py`，生成 [static-audit.json](../artifacts/device/2026-11-10-prerecord/static-audit.json)。脚本固定本机 RTOS SHA-256，重新反汇编 schema、setter、分派与原生事件回调片段，直接读取 ARM 分派表，并列出当前已解析引用与资源计算。它只分析本地文件，不连接相机。

本轮完成的是实现条件和原厂残留路径的核查，**没有实现或真机验证一分钟预录**；下一步代码工作应围绕硬件编码流及 mux 接口，不能把 App 加一个“预录”按钮视为功能完成。
