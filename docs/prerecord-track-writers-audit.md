输出为 `artifacts/device/2026-11-10-prerecord/track-writers-audit.json`：29 条原始指令核对、25 组宿主执行验证全部通过；提取了两个 sensor 视频配置表共 176 项，并固定 18 个伪代码文件及函数体、两个未索引代码标签和三个表的 hash。模拟使用真实 helper，没有助手桩；输入轨道、内存和状态由主机构造。

## 主视频配置已追到 sensor 表

轨道在 movie 对象中的位置为 `movie + 0x78 + trackIndex*0x90`；每轨输入配置为 `cfg + trackIndex*0x34`。这两个偏移体系不能混用。

`AmpMuxer_InitMovieInfo(A0440CD4)` 的视频分支执行下列复制。证据为 `full/decompiled/a0440cd4.c:141–195`，以及 `A04410B4/A04410C4/A04410FC/A044110C/A0441180` 的真实指令。

| 轨道字段 | 输入字段或运算 |
|---|---|
| `+0x04`，换算目标比例 `D` | 所有轨道 `cfg+0x04` 的 LCM |
| `+0x08` | 原始 `cfg+0x04` |
| `+0x0c`，帧周期 `T` | `cfg+0x08 * (D / cfg+0x04)`；模式值为 1 时再加倍 |
| `+0x40`，源比例 `S` | 视频 `cfg+0x20` |
| `+0x78`，计数 `N` | `u16(cfg+0x28)` |
| `+0x7d`，模式 `M` | `u8(cfg+0x2d)` |
| `+0x7e`，偏移初始化控制 | `u8(cfg+0x2e)` |
| `+0x7f`，VFR factor | 初始值 1 |

主 MP4 open `A01F3338` 在 `a01f3338.c:116–171` 先清零配置，再把 sensor 视频配置返回值 `v` 的 `u32(v+0x10)` 同时填入 `cfg+0x04` 和 `cfg+0x20`，将 `u32(v+0x0c)` 填入帧周期。原始指令 `A01F38E0/A01F38EC` 与 `A01F3900/A01F3904` 对应同一个值的两次读取、两处写入。

同一路径把 `M` 显式设为 0，`cfg+0x2e` 保持默认清零；`N` 来自第二个 sensor 回调返回结构的 `+0x04`。因此已检查的主视频 open 路径初始 `F=1,M=0`，无需预先套用重排/双帧分支。

两个 sensor wrapper `A0225B38/A0225BB8` 从注册对象 `A13C879C` 的 `+0xcc/+0xd4` 取得回调。注册函数 `A02257EC` 复制整个 0x120 字节配置；已导出的注册配置构造函数 `A018623C` 在相应槽中填入 `A0184F10/A018488C`。本轮宿主执行注册构造函数并在调用注册前停止，读取这两个槽，确认地址一致。两个回调标签有原始指令和 listing，当前 `functions.json` 没有对应函数项，因此报告明确以字节范围固定，没有伪造反编译文件。

`A0184F10` 按状态 `A13C88C9` 选择一个 24 字节步长的表：

| 输入选择值 | 表基址 | 内部 mode 0 的周期/比例 | mode 5 | mode 86 |
|---|---|---|---|---|
| 0 | `A06DCF78` | `1001 / 30000` | `1001 / 60000` | `1001 / 90000` |
| 1 | `A06E51B8` | `1000 / 25000` | `1000 / 50000` | `1001 / 90000` |

两表各取 88 项，对应回调 switch 的 `0..0x57` 索引范围。每行 `+0x0c` 是周期，`+0x10` 是比例。回调还会按状态修正尺寸，本轮只对上述时间字段进行验证。宿主直接执行每个选择值下的 5 个代表索引，返回地址、周期和比例均符合原始表；这不是相机上启用这些模式的验证。

另一个回调 `A018488C` 返回 `A06E4B38 + mode*16`。这张表的 88 行均为四个 u32 `(0,1,8,8)`，所以已检查配置源中的 `N` 为 1。运行时当前 mode 来自 `A021F854` 返回的 `A13C82B4`；本轮没有读取相机内存，**没有确认相机当前选择值、mode、已注册回调或二级码流覆盖配置**。

现在能够确认的是：原生 mux 预期按所选 sensor 表的比例解释视频描述符 PTS，**源比例不是固定 90 kHz**。硬件编码器是否在全部模式、切换和异常条件下严格满足该约定，仍需独立生产者证据或后续样本确认。

## 原点取自首次消费的描述符

`IsoMux_ProcessVideo(A042D0F8)` 在 `a042d0f8.c:172–177`、原始指令 `A042D378–A042D394` 检查：

```text
if (track.origin58 == 0 && track.frameCount48 == 0)
    track.origin58 = descriptor.PTS08;
```

这发生在本轮对应的帧类型分支和 `IsoMux_WriteVideoFrame` 调用之前。它是该消费路径首次处理描述符时选取的原点，不能据此声称捕获时钟以 UNIX 时间、系统启动或录制按钮为 epoch。

本轮宿主运行该指令前缀，验证初始原点及计数均为零时完整复制超过 u32 的 PTS；计数非零或原点已有值时保持原值。若首个 PTS 本来是零，防止后续重设原点的另一个条件来自帧计数推进。

## 初始化、DTS 推进和恢复分别写哪些字段

`InitPTS(A03E5AB8)` 保留上一报告中的规则：偏移控制 `+0x7e==0` 时将 `-low32(T*(N-1))` 的 64 位模式写入 `+0x68`，并清零 `origin58`、`convertedPTS60` 和 `frameCount48`。主视频配置 `N=1` 因而初始偏移为 0。

正常帧写入成功后，`IsoMux_ProcessVideo` 和 `IsoMux_ProcessAudio` 都调用 `A0440948` 推进轨道。该函数的 `UMLAL`（`A0440960`）与写回（`A0440984/A0440988`）确定：

```text
track.DTS20 = add64(track.DTS20, u32(T) * u32(entryCount))
track.next28 = track.DTS20
track.counter10 += entryCount
track.counter14 += entryCount
if (track.type89 == 1) track.frameCount48 += entryCount
```

这是已定位的正常 DTS 推进规则，证据 `a0440948.c:13–27`；它没有消除上一报告中 ConvertPTS 可调整周期、拒绝帧或进入其他类型分支的限制。

暂停恢复 `AmpMuxer_ResumePipe(A044180C)` 对视频轨道采用不同处理。令 `saved` 为 `movie+0x2b8+trackIndex*8` 的 u64，`current=track.DTS20`，则：

```text
track.bias68 = add64(track.bias68, sub64(saved, current))
saved = current
track.control7e = 0
track.frameCount48 = 0
track.origin58 = 0
track.convertedPTS60 = 0
```

原始证据 `A04418D0–A044190C`、`a044180c.c:50–83`。注意其中 `movie+0xe0` 对应 `track+0x68`，`movie+0xd0` 对应 `track+0x58`。这解释了为什么偏移不是只在初始化写一次，以及恢复后为什么会重新选择原点。本轮运行恢复函数到尾部通知调用之前，验证了偏移修正、重置和 snapshot 写回；没有执行 RTOS 通知、真实暂停或恢复生命周期。

## 普通 MP4 和 EventRecord 的音频时基不同

普通 MP4 `a01f3338.c:160–163` 的音频输入配置为：

```text
audio.cfg.scale04 = sampleRate
audio.cfg.period08 = 1024
audio.cfg.audioSampleRate1c = sampleRate
```

`sampleRate` getter 为 `A020FE74`，按音频索引读取 `A06D450C + index*0x1c`；本轮固定的前三项均为 48000。不能据此宣称索引上界已恢复，或其它动态配置永远不能改变采样率。

EventRecord `a01f845c.c:108–111` 则构造：

```text
audio.cfg.scale04 = videoScale
audio.cfg.period08 = udiv64(videoScale * 1024, sampleRate)
audio.cfg.audioSampleRate1c = sampleRate
```

这是两条路径在本轮已检查主轨配置处的差别，不应把普通 MP4 参数直接套到原生 EventRecord。

`InitMovieInfo` 将所有轨道比例归一到 LCM，并按整数倍率放大帧周期。`InitAudioTrack(A044042C)` 还把实际采样率单独存入音频轨道 `+0x40`；此处 `+0x40` 的角色不能套用视频源 PTS 转换。

| 构造的主轨配置 | 归一比例 D | 视频周期 | 音频周期 |
|---|---:|---:|---:|
| 普通 MP4：视频 30000/1001、音频 48000/1024 | 240000 | 8008 | 5120 |
| 普通 MP4：视频 25000/1000、音频 48000/1024 | 1200000 | 48000 | 25600 |
| 普通 MP4：视频 90000/1001、音频 48000/1024 | 720000 | 8008 | 15360 |
| EventRecord：视频 30000/1001、音频 48000 采样 | 30000 | 1001 | 640 |
| EventRecord：视频 25000/1000、音频 48000 采样 | 25000 | 1000 | 533 |

上表全部通过宿主执行完整原厂 InitMovieInfo 及其真实 helper 得到，并逐字段比对。EventRecord 的 25000 示例会在 `25000*1024/48000` 处取整；本轮没有确认是否有其他逻辑修正累计误差，不能忽略该截断或直接推断真机必然漂移。

音频消费者 `IsoMux_ProcessAudio(A043173C)` 读取描述符 payload 大小和地址、处理 EOS/暂停标记，写完一帧调用 `A0440948(track,1)`。该函数没有读取描述符 `+0x08/+0x0c` 的原始 PTS，也不调用视频的 ConvertPTS；其调用的跨轨限制检查使用轨道时间状态，而没有接收该描述符。证据 `a043173c.c:70–109,149–178`，以及 JSON 中完整函数的调用清单。此结论仅针对这条消费函数，不意味着音频采集生产者或系统其他部分完全不使用时间戳。

## 连续三帧的宿主验证

在普通 MP4 `30000/1001 + 48000/1024` 的构造配置下，本轮执行完整初始化，运行首描述符原点复制前缀，然后交替运行完整 ConvertPTS 和正常轨道推进函数三次：

| 原始描述符 PTS | 接受的 PTS | 推进后的 DTS |
|---:|---:|---:|
| 4886718345 | 0 | 8008 |
| 4886719346 | 8008 | 16016 |
| 4886720347 | 16016 | 24024 |

这次覆盖了 `N=1` 的正常同步成功分支，超出了上一报告仅验证算术前缀的范围。另有 `N=3` 和 `M=1` 的初始化构造用例验证字段复制及偏移/周期变化；这些用例不是已启用相机模式的证明。所有执行均不包含真实编码器、FIFO 并发、H.264 文件写入或 MP4 可播放性。

## 对一分钟预录的实际影响

旁路适配器现在可以按已恢复的配置来源显式建立视频比例、共同 mux 时基和正常 DTS 递推，无需猜测统一的微秒或 90 kHz 单位。采样合约还应保留所选 sensor 表及索引、movie/track 配置、首描述符原点和恢复 snapshot；只存原始 PTS 不足以完整复现时间线。

下一步仍应离线追踪编码输出事件 PTS 的生产者、暂停 snapshot 的更新时点和二级码流配置覆盖，并建立按共同剪切时点选择音频帧的模型。不能简单把每个轨道的首帧都各自归零后视为已经对齐：本轮尚无证据给出真实 FIFO 起始偏差、音频采样边界、模式切换连续性或预录截断点的音视频误差。

这些结果缩小了原厂时基和正常 DTS 的未知范围，但不构成相机端执行入口、可刷写补丁，也未验证并发 mux、60 秒 payload 保存、内存占用或真实恢复过程。
