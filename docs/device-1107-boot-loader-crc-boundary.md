# 启动期扩展：实际装载长度与双层 CRC 的离线联合探针

本轮把原启动包装器与后续取得的本机 PTB 合并核对，并用公开 BLD 原始装载函数做了有界 Unicorn 执行。没有连接设备、执行相机代码、输出修改后的分区/PTB 或生成升级包。

## 旧结论应如何更新

[启动期静态扩展评估](device-1107-static-boot-extension.md) 中“尚无本机 bootloader、完整 PTB”需要拆开看：后续已捕获本机 `VENDOR_DATA` 逻辑分区和其中 13 条用户分区记录，且 PTB、SYS_SW 数据 CRC 均能重算。**本机隐藏 BST/BLD/FW_UP、另一张 SYS PTB、物理 NAND/OOB 与独立恢复协议仍未取得。** 不能把已获得用户 PTB 写成完整启动备份，也不能继续笼统写为完全没有 PTB。

本机字段直接来自固定 SHA 的原始 `vendor_data.bin`，不是从 JSON 报告复制：

| 本机 SYS_SW 项 | 值 |
|---|---|
| 逻辑分区捕获长度 | `0x02000000` / 32 MiB |
| PTB record 偏移 | `0x48` |
| 实际长度 | `0x724f68` / 7,491,432 字节 |
| 装载地址字段 | `0x00100000` |
| 数据 CRC 字段/原值 | PTB `0x84` / `0xb3cb97f7` |
| PTB CRC 范围/字段/原值 | `[0,0x350)` / `0x350` / `0x59998e0c` |

原 7,491,584 字节分析窗口刚好是向 2048 字节页取整后的长度，比实际长度多 **152 字节**；这 152 字节并非全 FF。它们位于本机 PTB 记录的数据 CRC 范围之外，不能因为在分析窗口内就认作被装载的 RTOS 字节。PTB 实际长度对应的虚拟末端为 `0xA0824F68`，这也与原 MMU 布局中的已初始化数据末端常量一致。

## 新证据一：公开 BLD 的页读取与 RAM 写入边界

执行对象是公开 v1.10.52 `_part_bld.a9s` 的原始 A32 函数 `[0x10002358,0x100025e0)`。它**不是本机 1.10.7 隐藏 BLD**；仅验证该参考实现的具体行为。NAND 几何、坏块查询、页读取、无符号除法/余数、memcpy 与日志为显式宿主服务，其余装载器指令在 Unicorn 中执行。NAND/page 数据完全是本地输入。

16 个场景全部通过，包括：1/2047/2048/2049/131071/131072/131073 字节，各自覆盖首块正常与首块坏块；本机实际长度/256 分配块；以及下面的分配不足反例。合成数据每页不同，以便发现页或块游标错位。

- 本机长度场景读 3658 个 NAND 页，共 7,491,584 字节。
- 最后一个 NAND 页读入原厂 scratch `0x10032000`，只将余下的 1896 字节复制到目的 RAM。
- 目的 RAM 恰好写入 7,491,432 字节，逐字节等于本机捕获的有效前缀；之后 64 字节 canary 保持。
- 首块坏块场景跳过首块，后续源偏移与输出均正确。这只验证合成坏块查询返回值下的控制流，不验证实际坏块映射。

**新增反例：** 当描述符 `actual_size=0x20001`、`block_count=1` 时，装载器把遍历数量裁剪到 1 块，实际只写 `0x20000` 字节，未写最后 1 字节，但依然返回 `0`。这对应固定指令 `0x10002408/414` 的裁剪和 `0x100024fc` 的成功返回。因而该参考 loader 的“返回 0”不能单独证明完整装载，必须另核对实际长度与分配容量。这个反例不代表当前本机描述符有问题：本机 32 MiB 分配足以容纳约 7.14 MiB 有效数据。

完整窗口中调用的服务已经列出；本探针没有模拟上游全部启动验证或下游跳转。因此不能把本函数未调用数据 CRC 的结果升级成“启动链不校验数据 CRC”。

## 新证据二：原扩展跨越数据 CRC 与 PTB CRC 两个域

旧包装器的启动 BL 位于文件 `0x87bf4`，96 字节代码/字符串位于 `0x54e220`。两者均完全处于本机 `[0,0x724f68)` 数据 CRC 范围内。**代码页尾全零不是校验域之外的空间。** 即使不改变镜像长度，数据 CRC 也会变化。

仅在内存应用旧报告已有跨度、更新 PTB 数据 CRC 字段并重算表 CRC，结果如下；没有把修改后的二进制写出：

| 内存中的改动 | SYS_SW 数据 CRC | 相应 PTB CRC |
|---|---|---|
| 原始捕获 | `b3cb97f7` | `59998e0c` |
| 仅启动 BL | `1fc3e77e` | `866a0451` |
| 仅 96 字节包装器 | `d7f8e008` | `b0938f6c` |
| 两处同时 | `7bf09081` | `6f600531` |

两处同时修改的内存分区 SHA 为 `ad164130f9c9db4a61cb0ab8e3b1cf862cda7db320003e407e7d9e424c6546e5`，与旧包装器评估完全一致。若仅在 PTB `0x84` 更新数据 CRC 而保留旧 `0x350` 的表 CRC，表本身立即失配。

这只是字节与 CRC 的依赖关系，不是刷写步骤或启动接受证明。隐藏启动器可能还有副本选择、状态、签名、版本、坏块和更新顺序要求；本轮没有证明它们。

## 进入真机补丁前仍需的恢复合同

最关键输入仍是**在 SYS_SW 包装器执行之前就可进入、且不依赖当前 RTOS 成功启动的恢复通道证据**。要成立至少需记录以下事实：

1. 本机启动器身份和选择路径，能将本机 1.10.7 的入口/实际长度/CRC 检查与公开参考区分。
2. 独立进入条件及握手：相机停在目标 RTOS 初始化之前时，USB/UART/另一原厂启动分区仍可进入。Linux 节点和 RTOS 内的 `firmware_force.bin` 字符串不足以证明。
3. 恢复写入覆盖范围、完整性检查、坏块/OOB/副本规则及中断后的可恢复状态。逻辑 SYS_SW 捕获不能充当原始 NAND 救砖备份。
4. 冷启动和休眠恢复分别验收；原包装器受原厂初始化 flag 控制，移除 SD 不会撤销已写入 flash 的修改。

现有本地材料不能满足 1–3，本轮不输出可部署补丁或恢复工具。上表中的 CRC 计算不补足这些证据；新的装载边界结果也不证明页尾候选区没有运行期所有者。
