# YI 4K RTOS：gyro 环形区与帧事件契约

日期：2026-11-09。本文把当前静态反编译结果整理成下一阶段记录器的输入契约。地址对应社区 v1.10.52 RTOS 分区；本机是 `Z16V13L_1.10.7_build-20180202122459_git-a8f840ce_r2746`，不能把本文地址直接写入本机。

## 已确认的生产者顺序

`A0385780` 是由周期配置为 1000 的事件触发的采样与处理入口；固件调试字符串把这一路称为 1 ms，但实际计时频率仍需独立校准。它先读取 `A048E3F8()`，将结果写入采样 tick 字段 `A1702C40`，再把 gyro 驱动输出 `A1702C30/32/34` 写入三条原始环形数组。随后把本次 tick 发布到处理侧字段 `A170AB60`，推进 `A1702F14`，最后把刚写入的三轴值左移 8 位并更新偏置/积分数组。

可用于记录器的事实顺序是：

1. 取样 tick。
2. 读取并复制三轴驱动输出。
3. 写入原始三轴槽位。
4. 记录处理 tick。
5. 推进并环绕写指针。
6. 对原槽位做定点左移和后续状态更新。

因此，外部 Linux 轮询看到的槽位可能已经经历了第 6 步，也可能混合不同时间的字段；它不能构成无损 IMU 流。

## 环形区布局

初始化从 `A1702D00` 开始清空 9 组、每组最多 `0x84` 个 32 位槽位。每组起始位置相隔 `0x89` 个 word，末尾的一个 word 是该组的控制字段区，不属于数据槽。固件从 `A0757A90` 读出 30，并调用 `A0506690(1000, 30) << 2`，得到 132；本机只读快照也反复观察到 `A1702F10 = 132`。

| 组 | 起始地址 | 作用候选 | 证据 |
|---|---:|---|---|
| 0 | `A1702D00` | raw X | `A0385780` 写入驱动 X |
| 1 | `A1702F24` | raw Y | `A0385780` 写入驱动 Y |
| 2 | `A1703148` | raw Z | `A0385780` 写入驱动 Z |
| 3 | `A170336C` | X 偏置/积分状态 | `A0385780` 写入并由 `A0391CF0` 与 raw X 相减 |
| 4 | `A1703590` | Y 偏置/积分状态 | `A0385780` 写入并由 `A0391CF0` 与 raw Y 相减 |
| 5 | `A17037B4` | Z 偏置/积分状态 | `A0385780` 写入并由 `A0392CB0` 与 raw Z 相减 |
| 6 | `A17039D8` | X 逐行/辅助补偿 | `A0385780` 在 EOF 变化时填充 |
| 7 | `A1703BFC` | Y 逐行/辅助补偿 | `A0385780` 在 EOF 变化时填充 |
| 8 | `A1703E20` | 滤波后的 Z 状态 | `A0392CB0` 读写并送入 `A0384710` |

控制字段包括：

- `A1702F10`：环长度，当前为 132。
- `A1702F14`：下一个写槽；写入后按环长度归零。
- `A170AB38`：本次采样采用的槽位。
- `A170AB3C`：前一个槽位。
- `A170AB60`：处理侧最近采样 tick。

## 帧同步契约

EIS 主任务 `A0396F34` 等待图像事件对象 `A170BB88`：

- 事件位 `0x4` 来自 SOF 回调 `A03974D4`，回调时间在 `A170BC90`；主任务复制到 `A170BC88` 后发送 `0x100E`。
- 事件位 `0x8` 来自 EOF 回调 `A0397500`，时间在 `A170BA84`；主任务发送 `0x100D`。
- 事件位 `0x1` 来自 1000 周期定时器，主任务发送 `0x100F`，进入采样函数。
- 算法任务收到事件位 `0x10000` 后发送 `0x1010`，进入逐帧网格计算。

录像模式真正需要关联的是：`SOF → 曝光/行时序 → 1 ms 采样序列 → EOF → 0x1010 → warp 提交`。现有 48 条 gyro 日志和 66 条 frame update 只能证明这些路径有打印，仍不能建立逐帧一一对应关系。

## 记录器设计约束

下一阶段应在 RTOS 生产者侧复制固定结构到独立环形缓冲，再批量写文件或通过已有 IPC 导出。每条记录至少包含：`sequence`、raw X/Y/Z、采样 tick、使用槽位、SOF/EOF 快照、曝光偏移、生产者丢失计数。记录器必须有容量上限、发布顺序、cache clean/invalidate 和停止时 flush；不能在 1 ms 路径逐条 `printf`，也不能让 Linux 通过 `/dev/mem` 轮询 RTOS 私有缓存。

当前最小静态验证工具：

```sh
python3 scripts/rtos_ring_contract.py
```

它只读取保留的 RTOS 镜像，输出 JSON 契约，不接触相机。

## 对二开入口的影响

静态恢复的 `loadbin` 处理函数 `A02A2584` 只做三件事：检查文件、把文件读到给定地址、关闭文件并返回状态。它没有调用目标地址，也没有建立指令缓存同步或任务上下文。因此 `loadbin` 可以作为“把 payload 放进内存”的候选步骤，不能被当成已经打通的原生代码执行器。下一道独立关卡仍是找到安全的调用/跳转入口，并验证 ARM/Thumb 状态、I-cache、D-cache、寄存器保存和返回路径。
