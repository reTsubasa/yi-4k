# 预录候选：循环删除入口与普通模式隔离

2026-11-11，固件 `Z16V13L_1.10.7_build-20180202122459_git-a8f840ce_r2746`。本轮对已有 Ghidra 反编译导出做了一个有界的静态审计，专门确认 `DelLoopEncFile(A01F51D0)` 的调用门和删除游标更新顺序。没有连接相机，没有调用 API/setter，也没有写入固件、RAM 或分区。

机器结果见 [audit.json](../artifacts/device/2026-11-10-prerecord-loop-delete-gate/audit.json)，复现命令为：


## 已确认的静态事实

- `A01F51D0` 只有在 `deletedCount (A13C177C) < splitCounter (A13C29F4)` 时进入一次删除尝试。
- 删除对象由 `A13C2A38` 提供，调用 `A0224BF4(type=2, 0, id)` 更新数据库/素材游标；调用返回后才把 `deletedCount` 加一，成功时再把返回的下一 ID 写回游标。
- `A01F51D0` 在数据库删除前还会根据对象类型/编号尝试构造 `C:\DCIM\%dMEDIA` 目录并调用移除目录。该目录副作用仍依赖未展开的数据库 vtable 和文件系统实现。
- 自动开始路径 `A0120B28` 只在状态返回 `-4` 且 `A1055CFA == 6` 时调用 `A01F51D0`；卡满停止路径 `A0120F10` 在非 loop 模式直接走停止/错误路径，只有 mode 6 才调用删除；消息分派 `A011A208(param=2)` 同样只在 mode 6 调用删除。
- `A011A208(param=3)` 在非 mode 6 下明确记录并返回，不会落入循环删除函数。这与普通 event-3 切段尾通知的隔离结论一致。

## 对一分钟预录的影响

这轮把“普通模式切段会不会意外触发 loop 删除”进一步收窄为：在已恢复的四个调用点上，删除入口存在明确的 mode 6 门控；普通模式 event-3 的 param 3 不会直接进入 `A01F51D0`。因此预录候选不应打开原厂 loop 删除路径来承担临时片段回收。

仍然不能把该结论升级为安全的相机预录实现。恢复启动时复用旧游标、下一 ID 的筛选条件、数据库枚举失败、目录删除失败、掉电中断及真实文件归属仍没有运行期证据。尤其是 `A01F51D0` 的删除计数是“尝试次数”，删除失败时也会推进计数；若把它复用到独立预录目录，可能留下旧文件或误删不属于当前会话的素材。

推荐的预录后端仍是独立会话清单：每个临时段记录文件 ID/路径、首个同步帧和完成状态，只回收本会话已确认拥有的条目；不要调用 `A01F51D0`，也不要改变 mode 6 或隐藏 loop 偏好。相机侧真正实现前仍需只读取得运行期文件身份、删除游标和错误恢复证据。
