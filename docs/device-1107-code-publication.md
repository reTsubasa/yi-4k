# YI 4K 1.10.7：指令缓存操作与代码发布边界

## 本轮结论

在捕获映像的 **4 字节对齐 A32 扫描范围**内，找到 10 处指令缓存失效指令，没有找到
可作为普通可返回 `clear_cache(start, size)` 调用的独立函数。其中确有两处
inner-shareable 失效指令，但它们嵌在 BOSS 恢复流程中，不能把整段恢复函数当作刷新 API。

这是有范围的静态结果，不是“固件绝对没有代码发布能力”的证明。没有在真机上调用
这些函数，没有执行扩展代码，也没有验证多核传播。

## 可复现证据

运行：

```sh
.venv-reverse/bin/python scripts/device_execution_context.py
```

脚本固定实体机 RTOS SHA-256
`eee44c6c530183ece1e3872cb3e8958919a9aa418953899dbea8b9889987381c`，
逐个对齐字筛选以下 CP15 编码，再用 Capstone 解码核对：

| 编码 | ARMv7 架构层面名称/含义 |
|---|---|
| `MCR p15,0,Rt,c7,c1,0` | ICIALLUIS，inner-shareable 指令缓存失效 |
| `MCR p15,0,Rt,c7,c5,0` | ICIALLU，指令缓存失效 |
| `MCR p15,0,Rt,c7,c5,1` | ICIMVAU，按地址进行指令缓存失效 |
| `MCR p15,0,Rt,c7,c5,4` | 旧式预取刷新/指令同步编码，单独记录 |

扫描不依赖 Ghidra 是否识别为函数，覆盖捕获窗口内全部对齐字；数据或未使用代码也可能
匹配。没有发现上述 ICIMVAU 的对齐 A32 编码。没有扫描 Thumb、动态生成代码、未捕获
区域或所有可能的远程核心调度机制，不能据此宣称这些范围内也不存在实现。

结构化记录见 [code-publication-1107.json](../artifacts/device/2026-11-09-linux/rtos-analysis/code-publication-1107.json)，
指令证据见 [execution-context-evidence](../artifacts/device/2026-11-09-linux/rtos-analysis/execution-context-evidence/)。
脚本同时核对相关已导出函数与旧样本同体；literal 常量另从实体机字节读取。

## 失效指令所在上下文

| 指令地址 | 操作 | 上下文与限制 |
|---|---|---|
| `0xA03D0738` | ICIALLUIS | `0xA03D06C8`，BOSS resume，先恢复其他 OS/任务上下文 |
| `0xA03D0904` | ICIALLUIS | `0xA03D0780`，BOSS restore，还复制保存区、恢复映射和中断 |
| `0xA03D20C8` | ICIALLU | 上下文恢复区域，同时写 SCTLR/TLB 并跳往保存的 PC |
| `0xA03D2108` | ICIALLU | 同上，另一恢复分支 |
| `0xA03D2148` | ICIALLU | 同上，另一恢复分支 |
| `0xA04A2880` | ICIALLU | `0xA04A283C`，低功耗 cache 锁定/预取候选 |
| `0xA04A42D4` | ICIALLU | `0xA04A41E8`，MMU 页表初始化路径 |
| `0xA04A43CC` | ICIALLU | 同函数另一分支 |
| `0xA04A442C` | ICIALLU | `0xA04A43FC`，另一核心 MMU 初始化 |
| `0xA04A4490` | ICIALLU | 同函数另一分支 |

另一个匹配是启动入口中的 `0xA01001AC`，使用旧式 `c7,c5,4` 同步编码；它不是一个
带参数、可返回的函数。

### BOSS resume/restore

`0xA03D06C8` 的日志字符串标识为 `AmbaBossImpl_Resume`。它恢复固定系统任务并等待
事件标志，然后调用 `0xA03D0548`。后者重写保存的线程寄存器、TTBR1、辅助控制、
Context ID 和内存重映射相关 CP15 寄存器；之后才执行 ICIALLUIS。

`0xA03D0780` 还恢复多块保存区、注册固定中断处理函数并恢复另一任务对象。
这些调用要求完整 BOSS 状态，不能随意构造一个参数对象来执行缓存操作。

两处 ICIALLUIS 表明固件包含该架构操作；实际核心共享域、配置和完成性仍需运行期
证据。局部指令失效之前已经进行了大量恢复动作，不能跳入失效指令地址：后续代码
依赖原函数的栈和寄存器，而且该片段没有组成通用代码发布协议。

### MMU 与低功耗路径

`0xA04A41E8` 清理并建立页表，写翻译基址、域访问控制并包含 DSB/ISB；它不是
保留当前映射的 cache helper。`0xA04A43FC` 等待另一核心的同步标志，随后同样更新
页表状态；把它孤立调用可能等待不满足的启动条件或破坏当前映射。

`0xA04A283C` 会修改 `CP15 c9,c0,1` 并预取/锁定候选指令行，没有恢复原控制值，
也没有普通代码发布所需的完整语义。此前的“通用 I-cache 同步候选”判断已撤回，详见
[Shell 与缓存报告](device-1107-shell-memory-and-registration.md)。

## 下一步实现选择

现有 `0xA0498728` D-cache clean 只能解决数据缓存的一部分问题。扩展发布至少还需
明确写入者/执行者、目标内存属性、指令失效与屏障顺序，以及可能执行该代码的各核心
如何完成同步；Linux 与 RTOS 两侧不能仅凭虚拟地址相似就共享同一套假设。

继续实现前有两个可区分的方向：

1. 动态装载：继续恢复分配池所有权、首次调用入口和跨核心发布协议；当前没有可用 loader。
2. 启动时集成：在可恢复的固件副本中加入静态扩展和启动调用，复用原厂启动期映射与缓存
   建立过程；仍需核对镜像完整性、保留区、初始化阶段和回退方法，尚不能交付刷写版本。

第二条方向值得优先做离线设计：本轮没有找到适合直接复用的动态代码发布入口，继续
罗列固定回调无法补齐这一缺口。首先应核对启动时可预留的空间和补丁位置，而不是在
运行中借用系统恢复函数。
