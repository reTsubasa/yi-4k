# 1.10.7 低地址 PTB 读取通道：离线安全边界

本轮只分析本地已保存的固件、内核窗口和历史回执，没有连接相机、枚举设备、上传文件、执行目标命令或访问 `/dev/mem`。结论是：**普通 Linux `/dev/mem` read 明确拒绝这两个低地址；历史 mmap 快照不含 PTB 页；原厂 RTOS readb/readl/savebin 是有静态依据的后续候选，但尚未验证目标页运行时映射，不能据此声称读取无失联风险。**

这份报告接续 [PTB RAM 候选](device-1107-hidden-ptb-ram-candidate.md)，不把已经确定的指针再次算成新采集。SYS/USER 的实际低页内容仍未取得；BOOTSTRAP/BOOTLOADER/FW_UPDATER 的完整字节和独立恢复能力也仍未证明。

## Linux 路径的具体边界

输入是此前从本机 `/dev/mtdblock4` 取得的两个逻辑内核映像窗口，SHA-256 由脚本固定。`0x40008000` 为映像/符号偏移对应的平坦 VA 基址，未核对运行中内核代码。不能将这次反汇编表述为当前运行态测量。

`read_mem` 使用 `0x40017CCC` 的物理范围检查。开头直接构造 `0x3C9FFFFF`，当输入物理地址不大于此值，返回 0。原始 ARM 指令的四项本地仿真，包括 `PA 0x1400 / 0x1D0 bytes` 与 `PA 0x1800 / 0x354 bytes`，均走拒绝分支。这个结果解释了为什么普通 read 通道不能承担本次采集；它没有证明 mmap 通道同样拒绝。

`valid_mmap_phys_addr_range`（`0x40017D14`）只计算起始 PFN 加长度页数并比较 `0x100000`，不能提供低页属于普通 RAM、所有权、缓存一致性或可恢复性的保证。`devmem_is_allowed` 还调用资源检查，但相关函数不在这两个保留窗口内。本机旧配置含 `CONFIG_STRICT_DEVMEM=y`，这仍不足以从配置文字推导低页的运行时行为。

历史 `/proc/iomem` 只声明 `0x3CA00000..0x3FFFFFFF` 为 Linux System RAM。低页未列在其中，不能据此认定它是无害空洞或可直接读取的外设区。RTOS 的已有冷启动页表模型将 `VA A0000000..A064F000` 映射到 `PA 0..64F000`，属性为 Normal WB no WA，且不是当前 TTBR 的实际读取。两个 PTB 候选都处于同一 `PA 0x1000..0x2000` 页；从 Linux 新建不同缓存属性的别名不能保证一致，也不能反推历史死机根因。

另一个已有接口 `amba_dspmem_mmap`（`0x4027F694`）也不构成任意低地址读取入口：它锁 mutex，调用 `0x4002049C` 取种类 1 的区域，要求请求 VMA 长度等于返回的完整区域长度，并用返回物理基址覆盖 `vm_pgoff`。区域 getter 经过 RPC 和 cache 操作取得参数，不接受本次 PTB 地址作为任意输入。不能因为接口名字带 mem 就尝试它。

## 已有快照中有没有低页副本

脚本枚举 `artifacts/device/2026-11-09-linux/rtos-readonly*` 下已有 `telnet-output.txt` 的 `YI_RTOS_MEMORY` 记录，共 14 个区间，全部不与 `VA A0001000..A0002000` 重叠。保留的 `rtos-window.bin` 从 `VA A0100000` 开始，也不含该页。这个结论严格限定于已枚举的历史直接 RAM 记录；没有声称任意固件数据中不存在间接拷贝。

历史 `vendor_data.bin[0:0x354]` 是已经验证的 USER NAND 表对照，既不是新 SYS 表，也不能冒充本次低地址 RAM 采集。相同值指针在另一个存储后端中出现，也只是多个实现使用同一目的 VA，不能视为找到另一个现成活动副本。

## 避开 Linux 别名的原厂候选

原厂 Shell `readb`（`A02A2E58`）和 `readl`（`A02A3000`）直接从传入 VA 读字节/32 位字，再通过 Shell 回调输出。共享解析器 `A02A2CFC` 只解析地址和 count：缺少 count 时默认 1；没有映射合法性检查、范围白名单、长度上限、异常恢复或溢出保护。`readl` 的 count 单位是 32 位字，不能把字节长度原样传入。

本轮在 Unicorn 中执行原始解析器和两个原始 handler，以合成低页替代目标 RAM，只 stub 固定有效参数的数值转换和打印回调。对两个表分别验证 count 0、1、完整长度，共 12 项：目标读取精确覆盖预期范围，所有 CPU store 仅在合成栈中，目标页无写入。SYS 完整表为 464 字节或 116 字，USER 为 852 字节或 213 字。这证明了已选路径的直接访存形状，没有验证真实数值转换器、真实打印回调、MMU、页当前所有权、看门狗或采集期间的表变化。

因此，不应把 readb 的“指令没有向该页写入”扩大成“执行不会使相机失联”。地址无效会使 RTOS 原生 load 异常，过长输出还会经过真实控制台/重定向系统。打印到 SD 时也会发生文件写入。

原厂 `savebin`（`A02A3DB0`）也是明确候选。它在 RTOS 上下文把给定 VA/长度交给原厂文件写入函数，避开新增 Linux 物理内存别名，但会写 SD 文件。它已经在其他区间验证过：`A0394BA0` 的 8 字节代码指纹、`A0FD7114` 的 48 字节 pool 头、`A14307B8` 的 220 字节任务对象，见 [原生诊断回传](device-1107-console-and-readiness-validation.md)。这些历史成功不证明 `A0001400/A0001800` 也已验证。

后续若要形成具体采集实验，应优先沿已有 RTOS 原厂文件/控制台路径，固定固件指纹、精确长度、输出回收契约和停止条件；还需单独解决低页当前映射/所有权证据以及失败恢复边界。本轮只交付离线审计，没有生成或部署读取脚本，也没有提出刷写试验。

## SYS 尾部新增解释与剩余未知

此前 SYS 的三个 0x40 字节分区记录在 `+0xCC` 结束，CRC 位于 `+0x1CC`。现在可进一步划分尾部最后 8 字节：

| 偏移 | 小端 word | 原始代码中的用途 |
|---|---|---|
| `+0x1C4` | `0x32746242`（字节 `Bbt2`） | BBT 主块 spare 标记 |
| `+0x1C8` | `0x42627433`（字节 `3tbB`） | BBT 镜像块 spare 标记 |

`A048372C` 的 BBT 构造路径选择最后两个可用块，保存至 USER `+0x348/+0x34C`，并在 `A0483810/A048381C` 写入上述 SYS 标记。`A0483570` 的 BBT 写入路径分别读取 `SYS+1C4/+1C8`，复制到 spare scratch 后，调用擦块/编程链。报告与脚本只分析它们，没有调用这些写入函数。标记用途由创建和消费两端相互支持，不是仅凭字符串猜测。

剩余 `[+0xCC,+0x1C4)` 共 248 字节仍未分类，不能统称为额外分区记录、引导镜像校验值或恢复数据。公开其他版本 BLD 的 PTB 接口与本机 RTOS 的固定地址不能证明本机 1.10.7 BLD 最初为何保留此页；这项来源仍未闭合。
