# EIS CPU 反馈标签、共享哨兵与完成边界

日期：2026-11-10。仅使用本机固定 ARM 镜像和已有 Ghidra 导出，未访问相机、`/dev/mem` 或修改固件。**已恢复原厂 CPU 对 `eis_update_addr + 0x3C` 的读取、解释和消费后重置链；CPU 发布标签与反馈解释具有相同的“子索引 + warp 就绪位”格式。尚未恢复非哨兵反馈值的写入者，不能把它升级为 DSP 锁存、编码帧完成或旧槽释放确认。**

## 纠正此前调用者结论

[DSP 参考边界](eis-dsp-reference-boundary.md) 中“`A02C61D4` 在已保留伪代码中没有发现直接调用者”的表述遗漏了 `focused/a0385780.c`。完整 `full/decompiled` 确实缺少该文件，但原因是巨函数 `A0385780` 反编译超时，并非它没有调用者。已有 `full/calls.tsv` 和 `full/references.tsv` 均保留两处调用；早先的 focused 导出还保留完整伪代码。此次将两个导出集合与固定字节合并核验，原有“没有直接调用者”负面结论不再成立。

两处固定调用站点为：

| 站点 | 调用实参 | 作用 |
|---|---|---|
| `A0387794..77A0` | `r0 = A170AFC8, r1 = 0` | 将共享尾部九个字段读到 CPU 缓存 |
| `A0387C8C..7CAC` | 缓存 `+0x20 = DEADBEEF`，`r0 = A170AFC8, r1 = 1` | 将消费哨兵写回共享 `+0x3C` |

源码参考均为反编译伪代码，不是原厂源码。此次关键指令直接按 SHA-256 固定的镜像核验，避免仅依靠恢复出的类型或函数名。

## 共享尾字段的实际 CPU 用法

`A02C61D4` 从全局 VCAP 对象 `+0x58` 取地址，用 `A04A3BD4` 转成 CPU 地址。该字段的注册来源已在 [间接 DSP 发布审计](eis-indirect-dsp-publication-audit.md) 恢复为发布字地址 `A0699160`。

| 相对共享发布字地址 | CPU 缓存地址 | 目前可证用途 |
|---|---|---|
| `+0x10` | `A170AFC8` | 读取，未在此次路径赋予完成语义 |
| `+0x20..+0x34` | `A170AFCC..A170AFE0` | 读取；其中低 16 位进入 skew debug port 配置路径 `A0383D80/A0384454` |
| `+0x38` | `A170AFE4` | 读取；gyro 处理后续分支检查是否为零，未证明是完成计数 |
| `+0x3C` | `A170AFE8` | 原厂日志称 `UpdateInfo.ArmSysTime`；读取后解析标签，再写 `DEADBEEF` |

读模式恰好复制 `+0x10` 与 `+0x20,+0x24,...,+0x3C`，没有读取 `+0x14..+0x1C`，也没有在此函数解引用共享字内的状态槽指针。写模式只把 CPU 缓存 `+0x20` 写到共享 `+0x3C`。空指针或未启用地址时返回零，不复制、不写入；因此返回零本身不代表读到了有效反馈。

`A03877AC..77D0` 首先拒绝 `FFFFFFFF` 和 `DEADBEEF`。有效分支在 `A0387920..795C` 做两种提取：

- 低 8 位存到 `A170AFC0`，用于选择历史记录和计算 `ucodeSampleTime`；
- `0x100` 位存到 `A170AFC4`，原厂日志把它命名为 `WarpReady`。它为零且相关功能启用时，会打印 `Warp content not ready last frame`。

原厂固定字符串补强了字段解释：`A0600130` 为 `Spf[ArmSysTim]=... ArmSysTim=... (ucodeSampleTime=...); WarpReady=...; Ptr=...`；`A0600228` 为 `current UpdateInfo.ArmSysTime: 0x%x ...`。这些名称能支撑 CPU 对字段的理解，不能证明 DSP 的写入指令或实际执行。

消费有效标签后，CPU 会清除本地两个就绪状态，检查反馈间隔过长/过短的日志条件，将 `DEADBEEF` 写回共享 `+0x3C`，并保存当前 CPU 时间。该时间更新位于 `A0387CB0..7CC4`，不是递增的 DSP 完成序号。读、解析和重置之间也没有在已审阅指令中显示出原子交换、读版本重试或 cache invalidate；不能仅凭这个协议形状排除并发覆盖。

## 发布标签与反馈格式的关联

此次还沿着标签的 CPU 生产者反向追踪，结果超过“只读到某个状态值”：

1. `A0389FA8..9FC4` 读取字节计数 `A170AB1B`，减一后写入 `A1704310 + 0x20`。
2. 同一减一索引用于从 `A170B3A0` 起的历史记录，步长 `0x18`，保存采样时间差、X/Y 与两个 gyro 环位置等六个字。
3. `A038A624..A650` 在本地 `A170AFB8` 非零时，把 `0x100` OR 入该标签。`A0392CB0` 在生成了非零 warp 描述字段后设置这个本地状态；因此它至少是 CPU 的 warp 准备状态，不能直接称为 DSP 接收状态。
4. `A038B298..B2A8` 把 `&A1704310` 传给 `A02C5FD8`。固定 `A02C6080/6084` 将原状态 `+0x20` 完整复制到选中的状态槽 `+0x20`，随后发布状态槽地址。
5. 反馈低 8 位又选择相同的历史记录，并恢复 X/Y 与两个 gyro 环位置；bit 8 按 `WarpReady` 检查。

这构成**CPU 发布字段和反馈解释的格式匹配**，是继续寻找 DSP 反馈写入者的具体线索。尚不能称为已证明的原样回显：没有恢复 shared `+0x3C` 非哨兵写入，也没有轨迹证明反馈对应某次发布。完整状态槽地址不在这次反馈解析中；不能据低 8 位推算槽 0/1。

该标签也不能当 MP4 帧号或单调完成计数。`A170AB1B` 是有条件递增、可清零的字节状态；固定 `A0388810..881C` 清零，`A0388830..8850` 将超出上限的值限制为 `0x40`。正常非零发布值由其减一产生，CPU 发布的子索引范围为 `0..63`，后续可重复；这里没有与编码帧号、PTS 或持久录制序列关联的指令证据。

## 后续任务与间接回调边界

反馈读取不是一个“DSP warp 完成专属回调”直接触发的函数：

```text
timer callback A03974C4
  -> event flag A170BB88 |= 1
  -> EIS task A0396F34 sees flag 1
  -> image_command_dispatch(0x100F)
  -> A03B1ECC / A03AF31C
  -> A0385780
  -> A02C61D4(read / reset)
```

`A0396F34` 将 `A03974C4` 放入 timer 配置，两个配置数值为 1000；本报告不猜测这些配置数值的时间单位。固定 `A03972CC/72D0` 证明事件位 1 选择 `0x100F` 路径。该任务还向通用 DSP 事件注册器 `A02C11B0` 注册：

| 事件编号 | 回调 | 回调动作与任务后续 |
|---|---|---|
| `0x1A` | `A0397500` | 取 CPU 时间和一个间接传感器参数，置事件位 4；任务调用 `0x100E` 的 SOF 路径 |
| `0x1C` | `A03974D4` | 取 CPU 时间，置事件位 8；任务调用 `0x100D` 的 EOF 路径 |

通用注册器把回调加入运行时数组，`A02C1358` 以 `blx r3` 调用已注册指针；停止流程通过 `A02C1298` 清除注册。这里恢复了真实的间接分发关系，但这两个回调没有读取共享 `+0x3C`，也没有在审阅路径中释放状态槽或 warp 表。不要把 SOF/EOF 通知误命名为 warp latch 或旧表回收。

## 离线验证及可复现范围

```sh
.venv-reverse/bin/python scripts/audit_eis_completion_state.py \
  --output-directory artifacts/device/2026-11-10-eis-completion-state
```

固定镜像基址 `A0100000`，SHA-256 `eee44c6c530183ece1e3872cb3e8958919a9aa418953899dbea8b9889987381c`。输出 [audit.json](../artifacts/device/2026-11-10-eis-completion-state/audit.json)、[audit.asm](../artifacts/device/2026-11-10-eis-completion-state/audit.asm) 和 [脚本](../scripts/audit_eis_completion_state.py)。验证包含：

- **63 条固定指令检查**，覆盖字段搬运、标签生成、消费哨兵、发布调用和回调分发。
- **4 个 helper 场景**：九字段读取、仅重置共享 `+0x3C`、空指针和禁用地址。
- **128 组标签/槽发布/读回/重置**：64 个正常子索引 × 两种 warp 就绪位，执行原始 ARM 代码；合成反馈由测试主动注入，并非 DSP 回显。
- **4 个实际守卫分支**：两个哨兵走无效路径，0 和 `0x13F` 走有效路径。
- **3 次没有新反馈的 CPU 发布**：共享 `+0x3C` 一直为 `DEADBEEF`，生产者仍依次发布 `A06990E0 → A0699120 → A06990E0`，表明此函数自身不等待该反馈才回绕。

Unicorn 将 `A04A3BD4` 明确替换成返回合成共享基址的 stub，将 `A04A3B24` 替换成合成 identity 转换；没有执行真实地址映射、DSP、缓存或 MMIO。它验证 CPU 分支和赋值语义，不能当作真机一致性或发布延迟证明。本轮沿用已知无 REA MCP 的工具边界，没有修改注册或安装分析引擎，未生成新的 REA Evidence ID。

## 剩余的精确未知

目前已证明 **CPU 读/解释/重置共享哨兵**，已发现**可供静态关联的发布标签格式**；尚未证明 **DSP 写入 → latch → 完成 → 旧槽/旧表释放**。

下一步可围绕 DSP 的共享 `+0x3C` 存储追踪标签来源，验证是否取自 state slot `+0x20`、在哪一帧阶段写回，以及写回是否保证描述和表已经不再被读取。即使找到标签回显，也还需要证明缓存所有权、并发读写协议和最坏延迟。当前发现提供观测候选字段，不解除自定义 warp 提交的停止门槛。

## 既有真实日志的后续交叉核对

[真实反馈关联审计](eis-feedback-live-correlation.md) 已独立重解析原相机日志：83条有效反馈中66条位于录像几何阶段，均为索引5/6、WarpReady=1。该链路存在实际运行证据；原日志和成品另有61帧减13帧裁剪等于48帧的聚合一致性。详细历史/发布日志未启用，仍无逐帧绑定、DSP非哨兵写入或槽释放证明；不重复采集、更不将合成反馈当作真机。
