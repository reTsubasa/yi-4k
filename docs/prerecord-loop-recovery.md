# 原厂循环录像的启动/恢复游标边界

2026-11-11，固件 `Z16V13L_1.10.7_build-20180202122459_git-a8f840ce_r2746`。本轮只审计已有 Ghidra 反编译导出的启动、恢复和 loop 删除调用关系，没有连接相机、调用 API/setter 或写入固件、RAM、分区。

机器结果见 [audit.json](../artifacts/device/2026-11-11-prerecord-loop-recovery/audit.json)，复现命令：

```sh
python3 scripts/audit_prerecord_loop_recovery.py
```

## 恢复标志与计数器

`A01F4B8C` 将调用方传入的非零值写入 `DAT_A13C298C`，日志名为 `IsRestartRecord`。录像启动路径 `A0124470` 以 `DAT_A069B3C8 & 0x200` 作为该参数，因此“恢复/重启”状态来自相机内部状态位，不是由文件名或手机端决定。

`A01F4BC8` 在恢复标志为 1 时跳过初始化段；新会话则清零：

- 主文件 ID：`DAT_A13C2A50`
- 已生成分段计数：`DAT_A13C29F4`
- 已删除计数：`DAT_A13C177C`

loop 模式参数为 5 分钟时，单段时间为 60 秒；其它有限窗口使用 300 秒段，并以 `param_2 / 5` 作为保留段数。`0xffffffff` 表示不设置固定保留段数。这个映射是原厂循环录像的总窗口/分段逻辑，不是触发前一分钟预录。

## 新会话与恢复会话的游标差异

`A01F3338` 打开 MP4 时，loop mode 为 4：

1. 首次新会话先取得主文件 ID `DAT_A13C2A50`。
2. 如果 `IsRestartRecord == 0`，把删除游标 `DAT_A13C2A38` 设置为该主文件 ID。
3. 如果 `IsRestartRecord != 0`，不重新设置删除游标；同时保留已有分段计数和删除计数。
4. 随后递增 `DAT_A13C29F4`，创建新文件并继续 mux 初始化。

因此恢复路径确实依赖持久的旧游标/计数状态，但本轮没有找到“从 SD 目录重新枚举并校验游标属于当前会话”的证据。`A01F51D0` 后续只通过数据库 vtable 查询当前 ID、删除 type=2 条目并取得下一个 ID；它没有在已展开的函数体内比较文件时间、文件名前缀或会话 UUID。

## 恢复后的延迟删除门

新文件打开完成后，若本次是恢复会话 (`uVar7 == 1`)、保留段数不是 `0xffffffff`、且 `deletedCount < splitCount`，代码继续检查：

```text
retention_count < split_count - deleted_count
```

满足时发送 `0x48010003, param1=2, param2=0`。分派函数 `A011A208` 只在相机 mode 6（loop）调用 `A01F51D0`。这说明恢复后的删除不是无条件立即执行，而是由“恢复打开新段后，保留数量不足”触发的延迟 action 2。

## 对一分钟预录的边界

本轮新增了一个重要约束：原厂 loop 的恢复删除依赖旧的全局游标、分段计数和数据库“下一个 ID”枚举；它没有在当前静态范围内提供可证明的会话归属校验。删除失败时，已有 `A01F51D0` 仍会推进删除计数，可能留下旧文件或让计数与实际文件不一致。

因此不能把原厂 loop 恢复逻辑直接复用于一分钟预录。预录候选应维护自己的会话 manifest（文件路径/ID、创建时间、首个 IDR、完成状态），启动恢复时只接受 manifest 中明确拥有的片段，并在删除前核对文件身份。相机端实现仍需运行期只读确认数据库枚举、游标持久化、掉电后重启和存储错误路径；本轮没有执行这些操作。
