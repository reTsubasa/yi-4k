# ORC warp 表指针保留与复制准备边界

2026-11-10，全部离线。**标签回传前的 EIS 命令函数并没有在可见核心指令中消除全部表引用：描述符 `+0x0C` 的垂直表地址会保存到逐帧对象 `+0x18`，另有同类对象之间的浅复制；水平表 `+0x08` 则进入原厂 `idspdrv_dram2dram` 复制流程。** 这提供具体的生命周期证据，但没有证明硬件此后确实读表，也没有得到安全释放点。

本文承接 [标签反馈路径](eis-orc-feedback-path.md)。地址均为存储的 `orccode` 成员偏移，不是 ARM 地址或已经验证的 DSP 运行 PC。输入镜像和解码参考 SHA 固定，未知扩展指令保持原始字，不执行 ORC，也不套用未经验证的标准 delay-slot 模型。

## 垂直表地址保留在逐帧对象中

`0xD7454` 的入口建立以下对象别名：

```text
context = 原始 r3
state = 原始 r4
frame = lwz(context+0x654) + byte(context+0x65D)*0x68
```

固定指令 `0xD7490/94/A0/B4/D4` 分别给出 `0x68` 步长、字节索引、乘法、数组指针和选中对象。此处只称“逐帧对象”，未证明索引的运行期帧号或成品 PTS 对应。

命令分支把 `state+0x24` 指针交给原厂 `dram_2_smem`，再通过尚未解码的 staging helper，准备栈 `-80` 处 `0x50` 字节 warp 命令。本地首字检查为 `0x09005008` 后调用 `0x17F594`。从已有 CPU 描述布局可对照 [水平/垂直表字段](eis-indirect-dsp-publication-audit.md)。

调用返回后的核心指令明确执行：

| 来源 | 目的地 | 条件/伴随标记 |
|---|---|---|
| 本地命令 `+0x0C`，即栈 `-68` | `frame+0x18` | 非零才写 |
| 本地命令 `+0x37`，即栈 `-25` | `frame+0x1C` | 同一分支 |
| 本地命令 `+0x38`，即栈 `-24` | `frame+0x1D` | 同一分支 |
| `frame+0x20` 原值 | 原位置 | OR `0x800` |

这些是 `0xD76E8..0xD7710` 的普通 load/store，不依赖猜测专有指令的实际效果。描述符从外存到栈的实际传输仍属于前轮已说明的协议推断；这里证明的是**命令处理函数可见代码保留该指针值**。

标签路径 `0xD7844` 在 `0xD7948` 调用 `0xD7454`，返回后才跳到反馈准备块。因此标签提交的代码位置在这些保留指针的 store 之后。这个相对调用顺序不能升级为“硬件已经读完表”；也不能反向断言每次回显时硬件必然还在读表。

## 同类逐帧对象还存在浅复制和整对象交接准备

`0xC5844..0xC588C` 使用相同 `context+0x654` 数组与 `0x68` 步长，选当前/前一对象，包含下溢时按 `context+0x665` 的容量回绕，并将两个对象传给 `0xE3D74`。

`0xE3D74` 的 `0xE3DB8..0xE3DCC` 直接把源对象 `+0x18` 指针、`+0x1C/+0x1D` 两字节写入目的对象。这里复制的是指针字段，没有复制该地址指向的表。另需注意：其 flags 源掩码为 `0x7F8`，**不包含 bit 11**；不能把“指针被复制”写成“垂直 warp 被启用/同一个标记自动继承”。

另一条 `0xC49B4..0xC4A2C` 使用 `context+0x65E` 索引相同数组，取得目标句柄对应的 staging 地址，再把选中的整个 `0x68` 对象交给 `0x1A14D8`。这说明指针字段可处于整对象交接准备范围内。尚未把这个交接的接收对象、实际硬件消费和 `0x65D/0x65E` 的运行期先后关系闭合。

## 水平表进入原厂复制路径

`0x17F594` 从 warp 命令 `+8` 读取水平表地址，获取 command ID 20 的对象地址；水平表非零时准备：

```text
idspdrv_dram2dram(horizontal_table, command20_object+0x140, 0xC00)
```

helper `0x18CB2C` 的诊断字符串不是命名猜测：`0x18CC2C/30` 构造指向成员 `0x2BC474` 的地址，原文为 `idspdrv_dram2dram src: ... dst: ... size: ...`。

可见代码将源、目的、长度分别保存；以不超过 `0x220` 的 scratch 块推进，先调 `0x1A46A0(source,scratch,chunk)`，再调 `0x1A4A04(destination,scratch,chunk)`。`0x1A46A0` 的自身诊断是 `dram_2_smem(), size is not multiple of 4`，区别于之前找到的要求 128 对齐的 `0x1A4890`；写回 helper 是此前确认的 `smem_2_dram`。尾部小于等于 63 字节另有读取/保持 padding 的准备路径，窗口一并保留。

这些事实支持原厂复制方向，**不证明复制完成后才返回**。特别是 `0x1A46A0` 调用 `0x1A6EF4` 后，又调用 `0x1A156C`；后者包含循环、计数和未知 `FC606000/FC60001C/F0000049` 等扩展字。没有出现可独立识别的 done 状态普通寄存器轮询，不能把函数擅自命名为 DMA 完成等待或 barrier。水平表是否已可释放，也仍依赖这些硬件语义。

## 可复现审计与剩余问题

```sh
.venv-reverse/bin/python scripts/audit_eis_orc_table_lifetime.py
```

[固定字节审计脚本](../scripts/audit_eis_orc_table_lifetime.py) 通过 **96 条核心指令、2 处原厂诊断字符串引用**。完整指令窗口、未知字、输入身份和窄结论在 [audit.json](../artifacts/device/2026-11-10-eis-orc-table-lifetime/audit.json) 与 [table-windows.asm](../artifacts/device/2026-11-10-eis-orc-table-lifetime/table-windows.asm)。本轮没有设备连接、ORC 执行、RAM 写入或固件修改。

现在可以明确：单靠状态槽 tag 回传，无法从已恢复的代码证明垂直表引用全部终止。后续应优先恢复 `frame+0x18` 的真实接收消费者，以及 `0x1A156C/0x1A6EF4` 等扩展指令的复制完成语义，补齐帧身份、硬件最后一次读表和缓存可见性证据。没有证明“反馈不安全”的实际事故，也没有获得可安全复用的释放协议；自定义 warp 提交和算法替换仍未上机。
