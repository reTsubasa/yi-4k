# 1.10.7 非缓存池：分配、释放与首次调用边界

## 池来源和现有使用者

[页表审计](device-1107-noncache-executable-ram.md) 已确认 `A2100000..A3100000` 的初始构造属性为 Normal non-cacheable、XN=0、AP=3、S=1。启动函数 `A018756C` 在 `A018766C` 调用 `A03BC6B0(A0FE7220,A2100000,01000000)`，建立此 secondary byte pool。

`A0187698 -> A01E66F4` 随后保存两个池指针：缓存应用池 `A0FD7114` 到 `A13A23E4`，NC secondary pool `A0FE7220` 到 `A13A23F0`。本轮枚举固定设备引用索引中这两个 NC 地址的全部 15 条引用，并按实际函数体归属记录在 JSON 中。它们证明下列原厂用途，而不是一份可供扩展随意覆盖的内存清单：

| 已有路径 | NC 分配/传递 | 所有权和生存期含义 |
|---|---|---|
| `A0186F3C` 中间件初始化 | 从 `A0FE7220` 对齐分配 `20000` 字节；原始地址存 `A104E590`，对齐地址交给中间件/DSP 初始化 | 子系统拥有；不是对外借出的缓冲 |
| `A0189A28` 音频工作区 | 从 `A0FE7220` 分配，aligned=`A105376C`、original=`A1053674` | 重配置及 `A018AE80` 用 original 释放；不能沿用旧指针 |
| `A01CBBBC`、`A020CF14` 音频输出/解码 | 通过 `A13A23F0` 进入 `A03BC77C` | 工作区交给原厂音频对象，未见独占句柄交付给命令调用者 |
| `A0210894` 音频编码 | 通过 `A13A23F0` 对齐分配，original=`A13C7D14` | `A021064C` 释放 original 并清状态；数据供编码器使用 |
| `A01E0AB8`、`A01E0C10` 音频校准 | 直接从 `A0FE7220` 分配 NC 工作区 | 前者把区交给音频驱动；后者在校准尾部释放；错误分支并非通用回滚合同 |
| `A022F07C -> A04B2EE0` USB 初始化 | NC 池转存 `A1A4950C`，setup 再经 `A04B1C64` 存 `A1A454D8` | USB 子系统拥有池使用权，不能借其描述符当代码区 |

USB 的完整内部函数 `A04B1D18(&original,&aligned,bytes,alignment,type)` 在 `type=0` 时使用上述 NC 池，固定传 `FFFFFFFF` 无限等待；`type=1` 选择缓存池。它检查池是否非空，并向上层返回错误码，但不是 Shell 导出，也没有发布/执行新代码的合同。不应仅为分配而启动 USB 子系统或借用其等待路径。

## 可以复用研究的完整 API

| 原厂入口 | 参数与输出 | 检查和限制 |
|---|---|---|
| `A03BC6DC` | `(pool,&out,bytes,timeout)` | `timeout=0` 不等待；`FFFFFFFF` 保留无限等待；其余换算。调用 `A03C3448` 检查层 |
| `A03BC714` | `(original)` | 跳至 `A03C3700`，通过块头找所属池；必须传原分配地址 |
| `A03BC77C` | `(pool,pair_out,bytes,alignment)`；`pair[0]=original`、`pair[1]=aligned` | 固定不等待；申请 `bytes+alignment`；除法余数实现一般向上对齐，alignment=0 时保持原地址 |
| `A03BC7D0` | `(pair_out)` | 读取 `pair[0]` 后释放；不会清空旧输出指针 |
| `A029A7D8` | `(pool,&aligned,&original,bytes,alignment)` | 固定等待 500；effective alignment 至少32；申请 `bytes+2*effective`，用位掩码对齐；没有检查 alignment 是2的幂 |

`A03C3448` 检查池非空和 `BYTE` 魔数、输出指针非空、`0 < bytes <= pool.region_size`。有等待时先检查 system state，随后排除 timer-thread/不允许的调用上下文。实际分配 `A03BCD20 -> A03BD130` 把申请向上取整到4字节，使用带自旋锁和核心标识检查的链表查找、合并及分割；成功后将块头 owner 写成池指针。无可用块且 timeout=0 返回 `10`，没有把结果指针覆盖为 NULL，因此调用者必须以返回码决定能否消费输出。

这些检查不等于地址探测防护：输出指针只检查非空，释放器也必须先读取输入前的块头。它们不验证调用者随意构造的指针可读写；interior/伪造/失效指针可能异常或损坏状态。对齐包装的加法、位运算没有完整溢出和参数合法性检查，调用者必须先限制申请大小和对齐值。不要只依赖底层池大小检查来修复上层整数回绕。

一个成功分配的块归该分配持有者，直到用 original 成功释放或池被删除/重建；释放后可能被其他等待任务立即取得。对齐地址通常位于块内部，不能用它代替 original。若区已经交给任务、音频、USB 或 DSP，CPU wrapper 返回不代表消费者结束，也不意味着可以释放或改作代码。

## 合成执行实际验证了什么

脚本在完全合成的 `A0000000..A4000000` 和主机测试栈中载入固定原始代码，创建自己的 16 KiB 测试池。测试控制块是 `70003000`，数据地址形状为 `A2100000`；这不是对真实 `A0FE7220` 的创建、分配或快照。

声明的 RTOS 状态为 core 0、当前/待执行任务指针相同、无中断状态、无其他已创建池、无等待任务、无锁竞争。随后实际执行原厂 pool create、checked allocate/free、search/split/coalesce、锁、MPIDR 查询、Thumb memset 和整数除法；没有以 mock 返回替代这些函数。测试拒绝进入 suspend/assert/context switch，并拒绝从池内取指。

39 次完整调用通过，包含：

- 创建后 `BYTE` 魔数、区域和大小正确；可用量 `3FF8`。
- null/bad-magic pool、null output、零/超池长度、非法等待/调用上下文返回相应错误。
- 37字节申请按4字节粒度处理，独立块头占8字节；两个同时存在的分配不重叠，释放另一块不会改动仍存活块的数据。
- 内存耗尽时不等待返回 `10`，输出槽保持旧值；双重释放和 null 释放返回 `3`。
- 7组 alignment 输入 `0/1/4/16/32/64/128` 验证 `A029A7D8` 的最小32及位掩码行为。
- `A03BC77C` 验证 original/aligned 输出顺序，`A03BC7D0` 使用 original 释放。
- 所有合法释放完成后，available 回到 `3FF8`；callee-saved 寄存器、SP 和返回地址保持。

这证明具体原码在声明的无并发模型中的 ABI、检查、基本独占和释放合同；它不证明真机当前空闲量、最大连续块、任务竞争、fragmentation 全部形态、DMA 生命周期或实际缓存属性。

## 原厂命令是否补齐入口

`t ants` 第68项 `thumb` 的 handler 是 `A01A8998`，已用原始表字节核对。它包含名为 `malloc` 的分支，但这是缓存应用池 `A13A23E4` 的随机尺寸压力测试：最多50个槽，大小来自随机值 `% 28000`，分配后清零并打印 aligned/original 地址。失败会执行 `K_ASSERT`、关闭 IRQ/FIQ 后永久循环。达到50槽才触发批量释放；不是受控指定大小的 NC 分配与释放服务。

Shell 通用内存包装 `A02A8104` 从 `A144DAE0` 取得池指针，该指针由启动期 `A02A80F4(A0FD7114)` 设置。它检查分配返回并清零缓冲，但同样是缓存应用池；没有恢复出让外部请求者选择 secondary pool 的正常参数。

对固定69项 `t ants` 表，以既有直接调用索引向下6层搜索已识别的 NC 使用者，只找到 `rtmp_stop` 经音频重启路径到 `A0210894` 的候选调用链。这条路径依赖状态分支，会配置原厂编码资源，不能据此声称向调用者交付了独占缓冲。搜索不包含未知间接调用，不排除其他命令/未捕获代码；这里没有宣称固件全局绝无 NC allocator 命令。

## 首次进入和同步仍缺什么

完整分配函数解决“由谁拥有一块 NC RAM”，不会自动建立“谁能从 Linux/Shell 调用它、如何发布新指令、如何转入 entry”。正常调用这些 API 已要求在 RTOS 原生上下文中运行；当前没有恢复出可从外部输入传 pool/out/size 并拿回独占地址的安全调用器。

实际执行过的原厂锁有 DMB 和 DSB；它们用于保护池元数据。路径没有执行 ISB 或 I-cache MCR，不存在“完成代码写入后同步执行核心再进入输出地址”的行为。分配成功也没有清除或隔离旧用途可能留下的取指状态。不能把内部锁的屏障拼成未证明的代码发布协议，或把 NC 属性当作多核/首次取指完成性证明。

本轮新增可复用证据是：**资源管理 API 的正常检查、对齐、原始指针释放及基本生存期已经由真实原码离线验证。** 仍缺外部可达的独占分配与释放控制面、实际映射读回、写入者/执行者同步、首次控制转移及崩溃恢复。现有完整函数没有把这些阶段闭合为一条可上机方案。
